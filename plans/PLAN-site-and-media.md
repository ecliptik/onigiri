## Capturing the showcase stills and clips

README screenshots come from `testHeaderShots` (OnigiriUITests, opt-in `TEST_RUNNER_HEADER_SHOTS=1`). Retaken 2026-07-16 on the iPhone 17 / iOS 26.5 sim so the Liquid Glass floating tab bar + round + button shows (old shots were iOS 18's pinned bar, with a mismatched bar background on Goal).

**Why:** the user wants README shots to showcase the modern iOS 26 look with consistent rice-paper backgrounds and a uniform status bar.

**How to apply:** erase the sim first (`--seed-sample-data` ADDS Health samples each launch — totals double otherwise; iPhone 17 `B9DD19BB` is unpaired so a solo erase is fine), boot, `simctl ui … appearance light`, `simctl status_bar … override --time "9:41" --batteryState charged --batteryLevel 100 --wifiBars 3 --cellularMode active --cellularBars 4`, run the test with `-only-testing:…/testHeaderShots` + `-resultBundlePath`, then `xcrun xcresulttool export attachments`. README mapping: tab-today→today.png, tab-foods-library→foods.png (NOT tab-foods — that's the Favorites segment with one item), tab-goal→goal.png, tab-calendar→calendar.png. iPad (`ipad-landscape.png`, retaken 2026-07-16 on iPad Pro 13-inch/26.5): three iPadOS-26 gotchas — (1) the sim returns a PORTRAIT buffer for landscape UI (both XCUIScreen and `simctl io screenshot`); fix with `sips -r 270`; (2) windowed-apps mode pins a resize-handle arc in the window corner that never fades — switch the sim to Settings → Multitasking & Gestures → Full Screen Apps first (drove it with `axe tap --label`; no defaults key found); (3) visiting Settings leaves a "◀ Settings" status-bar breadcrumb — terminate+relaunch the app to clear it. testHeaderShots' final switchTab(to:"Today") fails on the iPad/26 sim after the search stops (tolerant section) — the tab shots all land first, so TEST FAILED there is harmless for capture. `ipad-landscape.png` retaken on the axiom-audit branch (d42440d) with the two-pane Today + sidebar — current. Health permission sheets on the sim IGNORE axe/HID synthetic taps (remote view) — only XCUITest's springboard driving works; don't retry coordinate taps.

**2026-07-24 recapture (v2.12.0 meal marks) — four traps, all now scripted.** (1) DEVICE: the committed showcase stills are **1206×2622** = iPhone 17 **Pro** (`65FE85CE…`); an iPhone 16 run produces 1178×2556 and silently RESIZES every site asset — check `Image.open(...).size` against the committed file before copying anything in. Erase its PAIRED watch too (`B5010BD4…`, shared Health). (2) AI COPY: the seeder deliberately leaves AI off ("AI-dependent tests opt in themselves"), which flips the scan row to "Scan Barcode or Nutrition Label" — the committed `foods.png` shows the AI wording. Fix: `simctl install` FIRST to create the app-GROUP container, `simctl spawn <udid> defaults write <group plist> aiEnabled -bool true` (+ aiProvider/onlineLookups/hasOnboarded), THEN run the test — the group container survives the test's reinstall. (3) CLIPS: don't hand-roll Health grants (the sheet is another process — no a11y tree, and a white-pixel probe for it fails outright in dark mode). Record against the sim testHeaderShots just left: already seeded, granted, appearance-set, 9:41. (4) The Favorites row order is RECENCY-driven and shifts between runs — resolve row coordinates from `describe-ui` MID-TAKE (one lookup per step ≈1s is affordable in a ~14s take; a lookup per tap is what outran the recording in 07-19). Clip encode to match committed: `scale=606:1318`, libx264, yuv420p, `+faststart`, `-an`; poster = frame 1 as jpg (606×1318). Scripts (prep/record/export, reusable) in this session's scratchpad.

**2026-08-02: capture the CALENDAR mid-month, or skip it.** The seeder writes only ~3 days of past burn+intake, so the month grid is populated only when "today" sits well into the month — the good committed shot was taken on the 24th (3 badges mid-grid). Seeding more history does NOT fix it (30 days still leaves 1 day in an early-month grid); only the capture date does. Stepping the grid back a month doesn't work either — the day card below still says "Today", which then belongs to a different month than the grid. Today/Foods/Goal have no such dependency and can be recaptured any day. Also: the AI-defaults dance in the note above is now MOOT for the four stills — the Foods entry doors were removed 2026-08-02, so no scan-row wording appears in any of them.

**2026-08-02 CLIP re-shoot — the whole recipe, now proven end to end.** All three clips drive one seeded sim with `axe` (labels, not coordinates) while `simctl io recordVideo` runs in the background; `kill -INT` the recorder to close the file. Four traps: (1) the app-group defaults must be set BEFORE recording or the scan row reads "Scan Barcode or Nutrition Label" and the AI clip's subject row doesn't exist at all — `xcrun simctl spawn <udid> defaults write <FULL HOST PATH to the container plist minus .plist> aiEnabled -bool YES` (the sim-RELATIVE path fails "Could not write domain", and `-bool true` silently wrote nothing where `-bool YES` worked; find the container by matching `MCMMetadataIdentifier` == group.com.ecliptik.Onigiri). (2) POLL for a string that only exists after the thing you're waiting for — the dark AI take grepped "Pork and beans", which is the SEARCH FIELD's own value from the moment it's typed, broke instantly, and recorded 18 s of spinner; "AI estimate from Apple Intelligence" is the real signal. (3) On-device inference is ~20 s COLD and <8 s warm, so no fixed sleep works: record long and concatenate two segments across the wait, cutting mid-"Estimating…" where nothing moves (19.1 s vs the committed 19.3 s). (4) The widget test REINSTALLS the app and resets the shared HealthKit grant — run it after anything depending on that grant. Interactions that worked: Add → tap the meal ROW (not its + button) opens the portion sheet with Contains → tap Log; day-swipe = Previous/Next day by label. Encode `scale=606:1318,fps=30`, libx264, yuv420p, `+faststart`, `-an`; poster = `-frames:v 1 -q:v 2`.

**2026-08-02 — TWO CONTAINER-METADATA TRAPS. Both render WRONG only in a browser; sips, Finder and QuickTime all show them correct locally, so verify site media by probing metadata, not by looking at it.** (1) CLIPS LOOPED THROUGH BLACK: `-ss` BEFORE `-i` leaves a non-zero start PTS and the muxer writes an EMPTY EDIT LIST (`elst` with `media time: -1`, `start_time` 0.8 s) which browsers render as black on every loop pass. Moving `-ss` after `-i` shrinks it to two frames but does NOT remove it (x264 B-frame delay), and `setpts=PTS-STARTPTS` doesn't either. What works: remux the finished mp4 through the CONCAT DEMUXER (`-f concat -safe 0 -i one-line-list -c copy`). This is why the two AI clips were already fine — they were built by concatenation to cut the inference wait, which rewrites timestamps as a side effect. Check with `ffprobe -show_entries format=start_time` (must be 0) and `ffprobe -v trace … | grep "media time: -1"` (must be 0 hits). (2) IPAD STILLS CAME OUT SIDEWAYS ON THE SITE: `sips -r 270` rotates the pixels AND writes EXIF orientation 8; sips/Finder honour the pixels, browsers honour the tag and rotate them back to portrait. Strip the tag after rotating (re-save the pixel data with no exif) and confirm `Image.open(p).getexif().get(274)` is None.

**WATCH `showcase/watch/home.png` — leave it in BALANCE mode (the user, 2026-08-02).** Asked to switch it to the kcal-left metric, I synced a goal + `balanceStyle=remaining` into the watch sim's app-group and it read "+609 kcal over" (orange); even with a perfect burn sync the best the fixture reaches is ~+127 over. The arithmetic is stuck: the watch's own DEBUG seed logs 1,235 kcal (420+610+205) while the burn that reaches a paired sim is ~1,029–1,505, and subtracting the ~400 kcal deficit target puts the budget under the intake every time. The watch also can't compute the resting ESTIMATE (no height sample reaches it, and DOB is an unwritable characteristic), so it can't get the phone's credited dayBurn. Offered to lower the seed's intake; the user said leave it. So the committed −270 balance shot stands and is CORRECT for a watch with no goal synced.

**WATCH `showcase/watch/home.png` (416×496, hard-won 2026-07-18).** The watch app has NO release seed path, but a DEBUG seed lives in `WatchModel.start()` (gated on `--seed-sample-data`) that writes a day via plain `logFood`/`logWater` on the REGULAR write auth. CAPTURE recipe: (1) erase BOTH paired sims — the pair is iPhone 17 Pro `65FE85CE…` + Apple Watch Series 11 46mm `B5010BD4…` (`simctl list pairs`); (2) seed+GRANT on the PHONE via `testHeaderShots` — this is the CRITICAL step: it determines the shared HealthKit auth so the watch's `requestAuthorization()` is a no-op. WITHOUT it the watch pops a "Health Access / Review" sheet that CANNOT be tapped on the watch sim (no `simctl` tap, no watch UI-test target); (3) build `OnigiriWatch` for the watch sim, `simctl install`, then `simctl launch <watch> com.ecliptik.Onigiri.watchkitapp --seed-sample-data` → the DEBUG seed's `logFood` writes into the now-authorized store (no sheet); burn (~1505) comes from the phone's shared seed, so balance ≈ food−burn (logging ~1235 kcal → −270 green). (4) `simctl io <watch> screenshot`. Paired sims share the phone's BURN to the watch but NOT the phone-written food, which is why the watch alone reads intake=0.

**2026-08-03 add-food re-shoot — ONE TAKE PER SEED, and the sleeps aren't the beats.** (1) The take LOGS a meal, so a second take on the same sim starts from the first take's damage: Today opened at "+170 kcal over" (orange) instead of "430 kcal left" (green). Every retry needs the whole cycle again — erase → testHeaderShots → AI defaults → record — so measure the timing on a throwaway take, then spend a fresh seed on the keeper. (2) `axe tap` returns 1–2.3 s AFTER the tap lands (`--element-type Button` is the slowest — it enumerates), and `simctl io recordVideo` starts 0.2–2.3 s after it's backgrounded; both vary run to run. So a fixed sleep is only the REMAINDER of a beat, and the trim must be measured from FRAMES, not from the script's own clock — print timestamps around each tap, then filmstrip the raw (`ffmpeg -ss N -frames:v 1`, hstack) to find the real cut. (3) The clip is now **9.5 s** (was 14.5): ~1.2 s of Today, ~3 s of the Log sheet, ~3 s of the portion sheet, then the logged toast. The old cut held the Contains rows six seconds. Sleeps that produced it: 1.4 lead / 1.4 / 1.6 / 3.4 tail. Encode + concat-remux + poster + all four probes are one script (`encode.sh raw.mov out.mp4 <ss> <dur>`), kept in this session's scratchpad.

## The social card

**2026-08-24 — the card has no generator, so here are its measurements.**
It was PIL-composed once (2026-07-16) and the script was never committed;
every later edit therefore starts by re-deriving the layout, which is an
hour each time. Measured off the committed PNG: canvas **1200×630**; face
**Helvetica Bold 80** (`/System/Library/Fonts/Helvetica.ttc`, index 1 —
confirmed by rendering line 1 and diffing it against the original raster,
which is indistinguishable); tagline left ink edge **x=91**; baselines
**352 / 454 / 556** (pitch 102, and the tops are NOT evenly spaced
because they follow each line's tallest ascender — measure baselines, not
tops); cream **#f3ead9**, accent/toast **#e3b36b**; icon + wordmark band
ends y=223; the URL line sits y 573–597, x 834–1107. Clean full-width
rows either side of the tagline: **379** and **565**.

**Editing it: MOVE the glyphs, don't re-render the ones you are keeping.**
Repaint only the band 380–564 by interpolating each column between rows
379 and 565 — the vertical gradient is near-linear over that span and the
interpolation matches the untouched rows exactly, so there is no seam and
no need to model the gradient. Then lift an existing line by solving for
its coverage against that same reconstructed background
(`a = (pixel − bg) / (textcolour − bg)`, red channel, clamped) and
re-composite that coverage at the new baseline and colour — this is what
lets a line change COLOUR or POSITION while staying the original raster.
Only render fresh when the glyphs don't exist yet (lower-case `health`
had no capital `H` to reuse). Two probes before committing: the vertical
step across rows 379/380 and 564/565 must be **0 levels**, and every
pixel outside the band must be **byte-identical** to what you started
from. Then the usual media check — `getexif()` empty (the `sips -r`
orientation trap) and the size still 1200×630, which `og:image:width`
and `og:image:height` both assert.

**The unfurl reads `og:description`, and ours was wrong for weeks.**
Slack and Signal render the `og:` tags; only Twitter/X prefers `twitter:`
and falls back. `twitter:description` carried the tagline while
`og:description` carried a different marketing sentence entirely, so the
preview never showed the tagline anywhere it was actually shared. Keep
BOTH on the same string, and keep them equal to what the card's own type
says. Verify against the LIVE page with `curl` — WebFetch converts to
markdown and drops meta tags. Slack and Signal also cache unfurls per
URL (~30 min); append `?v=N` to force a fresh fetch when checking.
